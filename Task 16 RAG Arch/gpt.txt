# 1. Business Problem

The company has approximately **200 historical client support tickets** stored as plain-text files.

Each ticket contains information about:

* customer's issue
* conversation/history

 RAG SEMANTIC SUPPORT TICKET SEARCH
EXECUTOR AGENT RUNTIME PLANNING SPECIFICATION

Purpose
-------
This document defines the runtime planning workflow for the Executor Agent.

The Executor Agent must NOT rely on a pre-created fixed task sequence for every
customer query. Every new customer support ticket is treated as a new Query.
For each Query, the Planner creates a unique runtime Query folder and generates
the task files required for that specific execution.

The runtime plan must be persisted under:

Task 16 RAG Arch/
└── Plan/
    └── <Query folder created at runtime>/
        ├── Task_01_*.txt
        ├── Task_02_*.txt
        ├── Task_03_*.txt
        └── ...

The exact Query folder name and task files are decided dynamically at runtime
by the Planner Agent.

1. RUNTIME INPUT
----------------
Input to the Planner:

Query = New support ticket from the customer.

Example:
"App keeps logging me out."

The Planner must analyze the Query and determine the execution steps required
to find relevant historical support tickets.

2. RUNTIME OUTPUT
-----------------
For every new Query, the Planner must create:

Plan/<Query folder>/

The Query folder should have a unique, filesystem-safe name. It may contain a
sanitized query identifier plus a timestamp or unique execution ID.

Example:

Plan/
└── Query_20260826_180500_App_keeps_logging_me_out/
    ├── Task_01_Analyze_Query.txt
    ├── Task_02_Prepare_Search_Query.txt
    ├── Task_03_Generate_Query_Embedding.txt
    ├── Task_04_Search_ChromaDB.txt
    ├── Task_05_Rank_And_Filter_Results.txt
    └── Task_06_Return_Search_Results.txt

The above tasks are examples only. The Planner must decide the actual tasks at
runtime based on the Query and available system capabilities.

3. EXECUTOR AGENT RESPONSIBILITY
--------------------------------
The Executor Agent executes the tasks generated by the Planner.

For each task, the Executor Agent must:

1. Read the task instructions.
2. Execute the required operation.
3. Validate the operation result.
4. Persist relevant output/artifacts if required.
5. Record success or failure.
6. Pass the resulting context to the next task.
7. Stop or recover according to the task's failure instructions.

The Executor Agent must not invent additional business steps when the generated
plan already defines the required workflow. If a task cannot be completed, the
Executor must report the failure and provide enough information for the planner
or recovery mechanism to decide the next action.

4. RUNTIME PLANNING LOGIC
-------------------------
The Planner should reason over the Query and create an execution plan.

The normal semantic-search workflow is expected to contain steps similar to:

A. Understand the customer Query.
B. Identify the customer's problem, symptoms, and useful technical concepts.
C. Prepare a search-oriented representation of the Query.
D. Generate an embedding using the configured embedding model.
E. Search the historical support-ticket embeddings in ChromaDB.
F. Retrieve candidate chunks.
G. Rank and/or filter the candidates.
H. Avoid excessive duplicate chunks from the same historical ticket when the
   business requirement is to return distinct historical tickets.
I. Return the top 3-4 most relevant historical ticket results.
J. Include ticket ID, matching chunk/text, similarity/distance score, and
   resolution status.
K. Preserve enough information for the support agent to judge the relevance.

GPT-5.6 Luna is required as part of the Query-understanding workflow. The
Planner may create additional GPT-related tasks when the Query requires them.

The Planner must not assume that every Query requires exactly the same number
of tasks. Task creation is dynamic.

5. IMPORTANT AI RESPONSIBILITY BOUNDARIES
-----------------------------------------
GPT-5.6 Luna:
- Understands and/or normalizes the incoming customer Query.
- May identify the issue, symptoms, entities, and technical concepts.
- May assist with reasoning over retrieved candidates if such a task is
  generated by the Planner.

Embedding Model:
- Converts historical ticket chunks into vectors during ingestion.
- Converts the runtime Query/search representation into a vector.
- The same compatible embedding model must be used for both document and query
  embeddings.

ChromaDB:
- Stores historical ticket chunk embeddings and metadata.
- Performs vector similarity retrieval.

Executor Agent:
- Executes the runtime tasks generated by the Planner.
- Does not replace the embedding model or ChromaDB.

6. HISTORICAL DATA ASSUMPTION
-----------------------------
Historical support tickets have already been or will be ingested into the
configured ChromaDB collection before runtime search.

If the required vector collection is missing or unavailable, the Planner may
generate an initialization/validation task or an ingestion/recovery task if
the runtime environment supports it.

The Planner should verify prerequisites before attempting semantic search.

7. RUNTIME TASK FILE REQUIREMENTS
---------------------------------
Each generated Task_<number>_<name>.txt file should contain enough information
for the Executor Agent to execute the task independently.

Every task should define, where applicable:

- Task ID
- Task name
- Objective
- Input
- Expected input/context
- Action to perform
- Tool/component to use
- Expected output
- Output location or artifact
- Validation criteria
- Failure condition
- Recovery/next-action guidance
- Dependency on previous tasks

Example task structure:

TASK ID:
TASK NAME:

OBJECTIVE:
What this task must accomplish.

INPUT:
Information supplied to this task.

ACTION:
Exact operation the Executor Agent must perform.

EXPECTED OUTPUT:
What successful execution should produce.

VALIDATION:
How the Executor Agent determines that the task succeeded.

FAILURE CONDITION:
What constitutes failure.

NEXT STEP:
What task/result should follow.

8. TASK DEPENDENCY MODEL
------------------------
Tasks should form an executable dependency chain.

Typical dependency:

Task 01
  ↓
Task 02
  ↓
Task 03
  ↓
Task 04
  ↓
Task 05
  ↓
Task 06

However, the Planner may create branching or additional tasks when required.

For example:

Query analysis
     ↓
Prerequisite validation
     ↓
 ┌───┴─────────────┐
 │                 │
Search preparation  Metadata/filter preparation
 │                 │
 └───────┬─────────┘
         ↓
    ChromaDB search
         ↓
    Result ranking
         ↓

9. TASK EXECUTION STATE
-----------------------
The runtime Query folder should be capable of showing execution progress.

Recommended task states:

PENDING
IN_PROGRESS
COMPLETED
FAILED
SKIPPED
BLOCKED

The Executor Agent should update task status or maintain an execution log so
that the runtime execution can be audited.

10. FAILURE AND RECOVERY
------------------------
The Planner should account for predictable failures.

Examples:

- GPT API unavailable.
- API key missing.
- Embedding model unavailable.
- ChromaDB collection missing.
- ChromaDB query failure.
- No relevant results found.
- Invalid Query.
- Malformed historical metadata.
- Embedding generation failure.
- Duplicate/insufficient results.

For recoverable failures, the Planner may create a recovery task.

For non-recoverable failures, execution should terminate with a clear failure
status and reason.

11. SEARCH RESULT ACCEPTANCE CRITERIA
-------------------------------------
The Executor Agent's successful search execution must produce:

- Top 3-4 relevant historical results.
- Ticket ID for each result.
- Matching historical chunk/text.
- Similarity/distance score.
- Resolution status where available.

The primary semantic-search acceptance test is:

Historical ticket:
"Session expires randomly every few minutes."

New Query:
"App keeps logging me out."

The correct historical ticket must appear within the Top 3 results.

This test validates semantic similarity rather than keyword matching.

12. QUERY FOLDER ISOLATION
--------------------------
Every new customer Query must receive a new Query folder.

Execution artifacts from one Query must not overwrite artifacts from another
Query.

Example:

Plan/
├── Query_001_App_keeps_logging_me_out/
│   ├── Task_01_*.txt
│   ├── Task_02_*.txt
│   └── ...
│
├── Query_002_Payment_failed_after_checkout/
│   ├── Task_01_*.txt
│   ├── Task_02_*.txt
│   └── ...
│
└── Query_003_Reset_password_link_expired/
    ├── Task_01_*.txt
    ├── Task_02_*.txt
    └── ...

The Query folders and their task files are runtime artifacts and must be
created dynamically.

13. SECURITY
------------
The GPT API key must be supplied through the application's environment
configuration, for example a .env file.

The Planner and Executor must never place the API key directly into:

- Task files
- Query text
- logs
- result files
- source code
- Git-tracked files

The .env file must be excluded from version control.

14. PLANNER DECISION PRINCIPLE
------------------------------
The Planner should create the smallest complete executable plan that satisfies
the customer's Query and the semantic-search requirements.

It should NOT blindly generate every possible task for every Query.

For example, if prerequisite validation has already established that the
embedding model is loaded and ChromaDB is available, the Planner should not
create unnecessary initialization tasks.

Likewise, if the Query requires additional interpretation or filtering, the
Planner may create additional tasks.

15. EXPECTED END-TO-END RUNTIME BEHAVIOR
----------------------------------------
For every new customer ticket:

1. Receive Query.
2. Create a unique Query folder under Plan/.
3. Analyze Query.
4. Dynamically generate the required Task_*.txt files.
5. Executor Agent reads the generated tasks.
6. Executor executes tasks in dependency order.
7. Each task validates its result.
8. Execution artifacts/results remain inside the Query folder where applicable.
9. Final task produces the ranked historical-ticket search result.
10. Execution is marked COMPLETED or FAILED.
11. A new customer Query starts a completely new runtime planning execution.

16. FUTURE EXTENSIBILITY
------------------------
The runtime planning design should allow additional tasks to be introduced
without changing the fundamental architecture.

Potential future tasks include:

- Query classification.
- Product/component identification.
- Resolution-status filtering.
- Metadata filtering.
- Result re-ranking.
- GPT-based relevance evaluation.
- Resolution recommendation.
- Confidence/relevance explanation.
- Human approval.
- Feedback capture.
- Search-quality evaluation.

These are optional extensions and should only be generated when the Planner
determines they are necessary for the runtime Query or explicitly enabled by
the system configuration.

FINAL DESIGN PRINCIPLE
----------------------
The Planner creates the runtime execution plan.
The Query folder stores the plan for that specific customer ticket.
The Task files define the individual executable steps.
The Executor Agent executes those tasks.
The plan is dynamic: different customer Queries may result in different task
sets and different execution paths.

The architecture therefore follows:

Customer Query
    ↓
Runtime Planner
    ↓
Create Plan/<Query folder>/
    ↓
Generate Task_*.txt files
    ↓
Executor Agent
    ↓
Execute tasks
    ↓
ChromaDB semantic retrieval
    ↓
Ranked historical tickets
    ↓
Final result
